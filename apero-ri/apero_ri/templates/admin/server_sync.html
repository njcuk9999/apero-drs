    What this does

    Server Sync keeps two (or more) ARI servers in step: users, per-user data, science groups, APERO profiles, comments, issues and the other categories listed in the Run tab. Each record is compared individually, deletions are propagated, and the newest change wins.

    • Complete mirror: changes flow both ways; when both servers changed the same record, the newest change wins.
    • Copy: this server only takes changes from the other server (the host). Local edits are kept until the host changes the same record.

    Never synced: the root (setup) admin account (-) and everything it owns, the Flask session key, backups, logs, caches, download links and every disk path. SSH aliases, mount points and local ports stay local and must be set in Local setup.

    Step by step (needs a super admin on both servers)

    1. On server B (the one you want to reach): open Admin Portal → Server Sync → Generate, give the token a label (e.g. the name of server A) and choose Read + write for a complete mirror or Read only for copy mode. Copy the token and B's URL. The token is shown only once.
    2. On server A: open Setup, paste B's URL and the token, pick the mode and click Test & add. The connection, token scope and clocks are checked (more than 5 minutes difference blocks syncing).
    3. On server A: open Run, choose the categories to sync and click Analyse. Nothing is written. Review what will be pulled, pushed, merged and the conflicts (records that differ with no shared history, or a new account whose email already belongs to another account).
    4. Resolve conflicts (take remote, keep local, skip always or allow the duplicate). You can also skip individual records. Then click Run sync now.
    5. After a successful run, switch on Automatic sync for the peer and make sure the Server Sync async task is active (default every 15 minutes). New conflicts found later are skipped and super admins are notified.
    6. Open Local setup on each server to finish records that need host-specific values (profile data paths, SSH aliases, mount points, ports).
    7. Optional: if server B should also run its own automatic sync with A, repeat the steps the other way round (generate on A, set up on B). This is not needed for a mirror: A pulls and pushes in one run.

    Security

    • The token itself never travels over the network. Each request is signed (HMAC-SHA256, with a timestamp and a one-time nonce) and every payload is encrypted and authenticated with a key derived from the token, so plain http:// links are acceptable. HTTPS is still preferable.
    • A token gives the other server read (and optionally write) access to all synced data, including password hashes, database credentials and SSH keys. Revoke tokens you no longer use in Generate.
    • Only super admins can see this page.
